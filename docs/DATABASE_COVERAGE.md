# MeiProof persistence coverage audit

## Inspection result

The current React app has 44 route paths in `src/App.tsx`. The frontend's direct Supabase PostgREST query is `organization_memberships.select('role').eq('user_id', userId)` in `src/lib/supabase.ts`; Auth signup/sign-in/session/reset use Supabase Auth. A FastAPI service now exposes authenticated claim, document, verification, buyer, lender and registry routes, and the frontend calls these routes for authenticated sessions. Demo login and the audit, anchor, notification, profile, preferences and search experiences remain local synthetic data or component state. The schema describes these workflows but does not make unsupported UI paths persistent.

## Table coverage checklist

The migrations define 31 MeiProof `public` tables: `profiles`, `organizations`, `organization_memberships`, `organization_access_requests`, `organization_access_request_events`, `claims`, `claim_lender_assignments`, `claim_documents`, `claim_line_items`, `document_extractions`, `document_extracted_fields`, `verification_runs`, `verification_findings`, `duplicate_candidates`, `claim_status_history`, `claim_buyer_responses`, `claim_lender_reviews`, `buyer_payment_records`, `risk_assessments`, `risk_assessment_factors`, `buyer_payment_risk_assessments`, `buyer_payment_risk_factors`, `audit_events`, `registry_reservations`, `registry_checks`, `registry_conflicts`, `registry_reservation_events`, `chain_anchors`, `notifications`, `notification_reads`, and `user_preferences`.

The two SQL migrations enable RLS for the core and added tables. Policies cover own profile/request/membership, claim participants, both sides of duplicate candidates, buyer-organization payment data, assigned lenders, targeted notifications, and own preferences/read status. Mutation grants/policies are restricted to profile/preferences/read status, seller evidence metadata, buyer responses, lender reviews and the reservation functions; approval, claim creation, assignments, extraction, verification, audit, and anchor writes require trusted/server-side workflows not yet connected to the UI.

## Seed scenarios and idempotence

`supabase/seed.sql` uses stable `fixture_key` upserts and inserts no Auth users, memberships, Storage objects or real document bytes. It has 4 synthetic organizations, 6 claims (including repeated invoice identity), 10 metadata-only documents, verification/extraction examples, a discrepancy, buyer dispute and lender review, payment history, two separate risk models, one active synthetic reservation plus an opaque competing-lender conflict, events, anchor placeholder and notifications. Because the seed has not run against PostgreSQL here, these are defined fixture counts, not observed hosted row counts. An RLS-safe user cannot read fixtures until a trusted membership/assignment is provisioned.

## Login/membership error diagnosis

The code signs into Supabase Auth, then calls the membership query noted above. A successful empty query produces `membershipRole = null` and sends the Auth user to the access-pending flow. A rejected PostgREST query is caught and its error text is displayed with `Workspace access could not be checked.` Therefore the reported message identifies a membership-query error, rather than an ordinary “no membership” result.

No hosted request/response was captured in this environment, so the actual remote cause (missing table, absent grant/RLS policy, wrong project, or other response) is **not diagnosed**. The local migrations create the expected table/columns and own-user select policy, and include a safe manual seller approval script at `supabase/admin/approve_existing_seller.sql`; none are applied remotely. Do not infer a successful login from the schema files.

## Frontend to FastAPI integration

The frontend uses `VITE_API_BASE_URL` (default `http://127.0.0.1:8000`) and sends the active Supabase access token as a bearer token. Authenticated claim list/create/detail, buyer organization lookup, private file upload/open, extraction, verification, duplicate lookup, buyer response, lender review, reservation, and reservation transition paths call FastAPI. Local demo login continues to use synthetic UI data and does not bypass backend authentication. The local API CORS allowlist covers `localhost:8443` and `127.0.0.1:8443`. No hosted request with an approved user token has been captured in this workspace.
